# The agent as an event consumer
### A filtered subscription and the CloudEvents envelope
- A **topic subscription** with a SQL rule passes only DeliveryDelayed, the filter pattern from Module 4
- The body is a **CloudEvents 1.0** envelope: `id` is the event id, `data` holds shipmentId and trackingNumber
- The publisher owns the schema; the agent reads only the fields it needs
- A new optional field breaks nothing, a removed or renamed field does
- Customer details enter a prompt only when the draft needs them

# Output as a command or an event
### A draft for review, a reroute proposal for a person to approve
- A **command** asks one named service to act; an **event** states a fact any service can use
- The draft customer message is the `NotifyCustomer` command (design), held until an operator approves it
- The reroute proposal is the `RerouteRequested` event, the one message the lab's agent sends
- A person approves through the reroute-approval endpoint, which raises `RerouteApproved`
- The agent never calls RerouteParcel: the routing service owns the van assignments

# Idempotency for agent consumers
### Check the processed marker before the model call
- Brokers deliver **at least once**: duplicate detection does not stop a redelivery after a lock expires
- `ReadProcessedDraft` checks agent-state for the event id **before** the model call
- A retry reuses the stored draft, because a second model call words it differently
- `SaveRerouteProposal` writes the `reroute-` proposal and the processed marker in one transactional batch
- `RerouteRequested` goes to parcel-events only after the batch succeeds

# Why the model call belongs in an activity
### Replay reads the recorded draft
- An orchestrator **replays its history** each time it resumes, so every call must return the same result
- A model returns different text for the same prompt, which breaks the first replay
- An **activity** runs once per attempt, and the runtime records its output in the history
- `CallActivityAsync` with `TaskOptions.FromRetryPolicy`: 5 attempts, 2 s first interval, backoff 2, 60 s maximum
- A waiting orchestration has no model call in flight, so a parcel can wait a day for a person

# Retries on throttling
### Which responses retry, and how a retry reuses the stored result
- **429** carries retry-after-ms, and the next attempt waits at least that long
- **408** from a provisioned deployment and **5xx** retry as transient failures
- **400** with code content_filter fails again, so the activity records the failure and stops
- An attempt can crash after the model answered, and the runtime runs the activity again
- The activity stores its result under the event id and returns it on the next attempt
