# Deploying with aspire deploy
### The AppHost declares the environment, one command provisions the rest
- `AddAzureContainerAppEnvironment` declares the environment in the AppHost
- `aspire deploy` provisions, builds and pushes the images, then deploys the apps
- The **managed identity** pulls the images, so you pass no registry credentials
- A CI job can build in the registry with `az acr build`
- `aspire destroy --yes` deletes the whole resource group

# Ingress and calls by app name
### Public endpoints only where outside clients need them
- `WithExternalHttpEndpoints` publishes an endpoint; without it a service stays internal
- `shipping-api` and `tracking-service` are the two public services
- Apps in the environment call each other by name: `http://shipping-api`
- `/health` maps in every environment, so it can be probed from outside
- `ExcludeFromManifest()` keeps `ops-console` and `exception-agent` local

# Key Vault access with a managed identity
### The same code runs on a laptop and in Azure
- `DefaultAzureCredential` uses the Azure CLI sign-in locally and the **managed identity** in Azure
- `SecretClient` reads secrets with that credential, so no password is stored
- Read access comes from the **Key Vault Secrets User** role, scoped to the vault
- `AddAzureKeyVault` and `WithReference` let Aspire assign the role
- The default is Key Vault Administrator; `WithRoleAssignments` narrows it

# Secret versions and rotation
### Key Vault events drive the rotation
- Each write creates a new **secret version**: `SetSecretAsync`
- Key Vault raises `SecretNearExpiry` 30 days before the expiration date
- Event Grid delivers it to a rotation function that writes the new version
- Restart the Container Apps revision so the container reads it
- Prefer managed identity; rotate only where a key is still needed

# App Configuration and feature flags
### Settings load at startup, flags refresh on their own
- The .NET provider loads key-values and feature flags into `IConfiguration`
- A **Key Vault reference** points to a secret that stays in the vault
- The AppHost declares the store in publish mode, `WithReference` grants a role
- Keys load at startup, so a new key needs a **revision restart**
- `UseFeatureFlags` and `IFeatureManager`, refreshed every 30 seconds

# Revision modes and traffic splitting
### Weighted traffic per revision and rollback
- **Single** mode is the default: the new revision takes over once ready
- **Multiple** mode keeps several revisions active for blue-green and canary
- `az containerapp ingress traffic set` sets weights that add up to 100
- Roll back with the same command and the previous revision at 100
- **Labels** (preview) give a revision a stable URL
