# Notification and state transfer events
### What the payload holds decides whether the consumer asks back
- A **notification** carries the fact, the identifiers and the time
- A consumer that needs more detail calls the owner in a second request
- A **state transfer** event carries the new state, and the consumer upserts its copy
- DeliveryDelayed is a notification, ParcelDelivered a state transfer
- Name events after business facts, such as **ParcelDelivered**

# The CloudEvents 1.0 envelope
### One envelope that consumers read without the producer's format
- Four required attributes: **id**, source, specversion and type
- Optional attributes are datacontenttype, subject and time; **data** carries the payload
- The id is unique per event, so consumers use it to detect duplicates
- The **subject** names the parcel, so brokers filter without parsing data
- Event Grid namespace topics and Dapr carry it; Service Bus carries plain JSON

# Failures that break event flows
### Each failure in one booking and the pattern that prevents it
- The **transactional outbox** stores the change and the event in one transaction
- The **idempotent consumer** records each message it has processed
- A **saga** undoes committed steps when a later step fails
- **Retries** with exponential backoff and jitter handle transient faults
- **Dead-lettering** moves poison messages aside; a claim check carries large payloads

# The booking saga
### Local transactions with compensations in reverse order
- A **saga** replaces one distributed transaction with local transactions
- Forward steps: ReserveCapacity, CapturePayment, PrintLabel
- **Compensations** release the capacity, refund the payment and void the label
- Compensations run in the reverse order of the forward steps
- Choreography fits a short flow, **orchestration** a growing one

# Retries and dead-letters
### Bounded retries for transient faults, a side queue for the rest
- Retry transient faults with **exponential backoff and jitter**
- Keep a finite retry count and a retry budget per dependency
- Give every outbound call a **timeout**
- Service Bus dead-letters a message after **ten** failed deliveries by default
- Event Grid dead-letters to a storage account once you configure it

# Messages, events and streams
### Service Bus, Event Grid, Event Hubs and Dapr pub/sub compared
- A **message** carries data under a contract, the shape Service Bus fits
- An **event** is a lightweight notification of a state change, for Event Grid
- A **stream** is a time-ordered series each consumer reads at its own pace, for Event Hubs
- **Dapr pub/sub** is a portability layer that sits on top of brokers
- Ordering, retention and dead-lettering decide most designs

# Takeaways
### What to carry into the Aspire module
- Start with a modular monolith and split when team, deployment, scaling or data demand it
- Use HTTP when the caller needs the answer, messages when the work only has to happen
- Draw boundaries where the business language changes
- Publish integration events after the commit, named after business facts
- Protect every flow with a pattern, and pick the broker by ordering, then retention
