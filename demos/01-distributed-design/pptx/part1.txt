# Designing event-driven distributed systems
### Where the seams of Grey Logistics belong before anyone writes a service
- **Boundaries**: a modular monolith or microservices, and event storming to find the seams
- **Messages**: HTTP or asynchronous commands and events, named and wrapped in CloudEvents
- **Reliability and brokers**: outbox, saga and idempotency, then one Azure broker per flow

# A modular monolith as the starting point
### Service boundaries inside one deployable unit
- Split for **team size**, independent deployment, scaling or data ownership
- A **modular monolith** deploys as one unit, organized into modules
- Each module owns its tables and exposes a small public interface
- Moving a module out turns its interface into the **service contract**

# Commands, events and queries
### What the sender expects decides the kind of message
- A **command** asks a named service to act and expects an action or a failure
- An **event** reports a fact, and the publisher does not know who listens
- A **query** reads current data and changes nothing, so HTTP GET fits
- Commands use imperative verbs, events use the past tense

# Request/reply and fire-and-forget
### Both styles appear in one booking
- With **request/reply** the caller waits, and HTTP is the default transport
- With **fire-and-forget** the broker stores the message until a consumer is ready
- Booking waits for ReserveCapacity, while ShipmentBooked waits in the broker
- **Temporal coupling** means both services must be up at the same moment
- Set each request/reply **timeout** from how long the customer will wait

# When HTTP is the right choice
### The Asynchronous Request-Reply pattern for long-running work
- The caller needs the answer for its next step, such as a **shipment ID**
- A **query** asks for current data
- Long-running work returns **202 Accepted** with Location and Retry-After
- The client polls until **303 See Other** points to the finished result
- If the caller only needs the work to happen, publish a command or an event

# The sticky-note grammar
### Business events on a wall, with the domain experts in the room
- **Events** are orange notes in the past tense, such as ShipmentBooked
- **Commands** are blue notes written as imperatives, such as BookShipment
- Actors issue commands, policies react to events, and **aggregates** decide
- **Hotspots** mark open questions, each with an owner and a date
- The big picture comes first, then the process level for one flow

# Domain events and integration events
### The same fact inside one service or across a broker
- A **domain event** is raised and handled inside one bounded context
- An **integration event** crosses a service boundary through a broker
- Integration events leave only after the entity is persisted
- The publisher owns the contract; the labs keep it in `Grey.Contracts`
- Every event also has a style: notification or state transfer
