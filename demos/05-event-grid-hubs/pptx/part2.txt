# Lock tokens in pull delivery
### Every received event stays locked until the consumer settles it
- `ReceiveAsync` reads up to 100 events and locks them for the consumer
- `AcknowledgeAsync` deletes the event for this subscription only
- `ReleaseAsync` makes it available again after 0, 10, 60, 600 or 3600 seconds
- `RejectAsync` dead-letters it, or drops it when no destination exists
- `RenewLocksAsync` extends the lock while the consumer still works on it

# Partitions and consumer groups
### Order holds within one partition, each group reads the whole stream
- Each **partition** is an ordered log, and order holds only inside one
- The van ID as partition key keeps one van's positions together, in order
- Events without a key go round-robin; a fixed partition ID lowers availability
- A **consumer group** reads the full stream at its own pace
- One active reader per partition and group, one checkpoint container per group

# Checkpoints and partition ownership
### A crashed instance's partitions resume from the last checkpoint
- `EventProcessorClient` stores ownership and checkpoints in a `BlobContainerClient`
- Instances claim partitions until the load is balanced
- After a crash, another instance takes over from the last checkpoint
- Delivery is **at least once**, so the handler must be idempotent
- **Capture** archives the stream to storage in Avro format

# The Kafka endpoint of Event Hubs
### Kafka clients keep their code and change their connection settings
- Port 9093 on the namespace (9092 in the emulator); a Kafka topic is an **event hub**
- Standard, Premium and Dedicated tiers; Basic has no Kafka endpoint
- `SASL_SSL` with **PLAIN** and a connection string, or **OAUTHBEARER** and an Entra ID token
- The message key picks the partition, so each van's positions stay in order
- Only gzip compression; treat Kafka Streams and transactions as preview

# SignalR Service modes
### Who holds the browser connections
- **Default**: your server hosts the hub, and the service proxies each client to it
- `AddAzureSignalR` on the `AddSignalR` registration, only when the connection string is set
- **Serverless**: a `negotiate` function and `SignalROutput`, with no hub server
- `withAutomaticReconnect` retries after 0, 2, 10 and 30 seconds
- **Web PubSub** fits when you need a WebSocket protocol of your own

# Checkpointing the van position processor
### A restart replays from the last checkpoint and skips no position
- `VanPositionProcessor` reads `van-positions` through the `ops-console` consumer group
- Each position goes out with `SendAsync` before `UpdateCheckpointAsync` stores the checkpoint
- Checkpoints live in the `ops-console` blob container in Azurite
- After a restart, the last pushed position can reach the map twice
- Test it: stop and start `telemetry-ingest`, and every van's sequence continues without a gap

# Takeaways
### What to carry into event sourcing and CQRS
- Publish `ParcelDelivered` once and keep its event type stable
- Give every subscription filters, a retry policy and a **dead-letter** container
- Offer **pull** delivery to partners that can't open an inbound port
- Key by van ID, read with one consumer group per service, keep handlers idempotent
- Push to browsers through **SignalR Service** in Default mode
