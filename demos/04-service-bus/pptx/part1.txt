# Overview
### Six reliability features for the parcel event flow
- Route each parcel event to the **subscriptions** whose filters select it
- Consume `tracking` with a **Functions trigger** that settles after its work
- Scale **competing consumers** with a KEDA rule on the backlog
- Keep each parcel's scans in order with **sessions**
- Dead-letter **poison messages** and drop duplicates with an idempotent consumer

# Topics, subscriptions and filters
### Each subscription keeps its own copy of the events it selects
- Each **subscription** receives a copy of every message its rules match
- `tracking` gets `ParcelScanned`, `customer-messages` gets `ParcelDelivered` and `DeliveryDelayed`, `exceptions` gets `DeliveryDelayed`
- A slow consumer builds a backlog on its own subscription only
- On Azure, every new subscription starts with a **default rule** that matches every message
- Rules on one subscription combine with OR, so delete the default rule

# Subscription rules in code and Bicep
### Correlation filters on Subject for every Grey Logistics subscription
- **Correlation filters** match fixed properties exactly; Microsoft Learn recommends them whenever they fit
- SQL filters add `LIKE`, `IS NULL` and `EXISTS` over properties, never the message body
- A rule action runs `SET` or `REMOVE` on the copy the subscription receives
- `ServiceBusAdministrationClient.CreateRuleAsync` creates rules in code
- The AppHost declares `AzureServiceBusRule`, and Aspire generates the Bicep

# Service Bus trigger and settlement
### The function completes a scan only after its work succeeds
- Isolated worker model with `Microsoft.Azure.Functions.Worker.Extensions.ServiceBus` 5.14.1 or later
- Bind `ServiceBusReceivedMessage` for metadata and `ServiceBusMessageActions` to settle
- Set `AutoCompleteMessages = false` whenever the function binds message actions
- **Settlement**: complete on success, abandon to retry, dead-letter a poison message
- An unhandled exception or an expired lock returns the message with a higher delivery count

# Concurrency, connections and hosting
### The trigger connects through the app's managed identity
- `maxConcurrentCalls` limits callbacks per instance: 16 by default, multiplied by the cores
- `maxConcurrentSessions` 8 caps the parcel sessions one instance works on
- `ServiceBusConnection__fullyQualifiedNamespace` and `__credential` replace the connection string
- **Roles on the subscription**: Data Receiver to receive, Data Owner for scale decisions
- `AddAzureFunctionsProject` places `scan-processor` in the `aca-env` Container Apps environment

# Competing consumers
### Replicas share the tracking subscription, and sessions keep each parcel in order
- Several instances receive from one subscription, and each message reaches one of them
- More instances raise throughput, and a failed instance doesn't block the others
- Parallel consumers give up ordering, so `tracking` requires **sessions**
- `ServiceBusProcessor`: `MaxConcurrentCalls` defaults to 1, `PrefetchCount` to 0
- Set `PrefetchCount` at least as high as `MaxConcurrentCalls`, and keep it small for slow handlers

# KEDA scale rule in Container Apps
### Replicas follow the backlog of the tracking subscription
- A custom `azure-servicebus` rule reads the depth of the `tracking` subscription
- **messageCount** sets the messages per replica: 5 by default, 10 in the lab
- The rule's `identity` reads the backlog with a managed identity instead of a connection string
- `minReplicas` 0 scales to zero, and `maxReplicas` caps the cost
- 60 waiting scans with `messageCount` 10 give 6 of the 10 replicas
