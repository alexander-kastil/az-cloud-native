# Point reads and queries
### Indexing and request charge on the tracking container
- Opt-out indexing: include `/*`, exclude `/_etag/?`
- A **composite index** on `scanType` ascending and `occurredAt` descending matches the ops console sort
- Log `RequestCharge` and `ActivityId` on every read you tune
- A **point read** by `id` and partition key skips the query engine and costs the least
- The partition key in `QueryRequestOptions` keeps the page query on one partition

# Session tokens for read-your-writes
### The token travels with the next request to another instance
- **Session** is the default consistency level: a client reads its own writes
- Each write returns a session token in `Headers.Session`
- Several web instances don't share the SDK's cached token
- The browser gets the token and sends it back with the next request
- Tokens are partition bound, so keep one per tracking number

# Cache-aside with change feed invalidation
### The projection deletes the cached tracking page after each scan
- **Cache-aside**: read `tracking:<trackingNumber>`, query on a miss, store with an expiration
- Five minutes plus up to 30 seconds of **jitter** spreads the expirations
- The projection upserts the scan first, then calls `KeyDeleteAsync`
- A retry repeats the idempotent upsert, and the TTL bounds a stale page
- In Azure: Entra ID through `Microsoft.Azure.StackExchangeRedis`, wired by Aspire

# Appending events with a version check
### The event ID carries the version, so a second append gets 409 Conflict
- One immutable event document per change, partition key `/shipmentId`, no `ttl`
- A correction is a new event: `PaymentRefunded` follows `PaymentCaptured`
- The ID `{shipmentId}-v{version:D6}` makes a second append for the same version collide
- `CreateItemAsync` answers **409 Conflict** and `AppendAsync` returns false
- `IfMatchEtag` protects documents that get replaced; append-only events don't need it

# Replay and snapshots
### Load from the newest snapshot and apply only the events after it
- `LoadAsync` queries one partition in version order and calls `Apply` per event
- The aggregate reads nothing but its own events
- A **snapshot** stores the state at one version, in the same partition
- 103 events: snapshot 100, then 3 `Apply` calls instead of 103
- The snapshot ID encodes its version, so a duplicate create gets a 409 to ignore

# Upcasting on read
### Stored events stay untouched, readers see the newest shape
- Past events are **immutable**: correct them with a compensating event or an upcaster
- An **additive** change adds an optional field, and tolerant readers ignore unknown fields
- A missing `serviceLevel` deserializes as null, and the reader applies `standard`
- `ShipmentBookedUpcaster` turns `schemaVersion` 1 into `ShipmentBookedV2` on read
- Upcasters chain one version per step, and every read runs them

# CloudEvents type and dataschema
### Consumer rules for each kind of schema change
- `type` stays the same across versions, `dataschema` changes with each one
- `source` plus `id` is the idempotent consumer's deduplication key
- Adding an optional field is safe for consumers that already run
- A rename writes both names for one release; a new meaning gets a new `type` or `dataschema`
- A consumer dead-letters a message whose `dataschema` it doesn't know

# Takeaways
### What to carry into the Dapr module
- Commit the event and its outbox event in one batch, relay with duplicate detection
- Make every projection idempotent: upsert under the event ID, await every write
- Keep reads on one partition, and send session tokens back for read-your-writes
- Delete the cached page after the upsert, and let the TTL bound the rest
- Put the version in the event ID, and evolve schemas additively or by upcasting
