# How replay rebuilds state
### The event history lets a second worker finish the booking
- Every scheduled activity, completed activity, timer and external event lands in the instance's **event history**
- A worker runs the orchestrator from the first line, and each `await` with a recorded result returns it at once
- After a crash, the next worker replays the history and schedules only `PrintLabel`, so the customer pays once
- Local variables come back from the history; the code never writes them to a database
- Between checkpoints the orchestrator leaves memory, so a long wait holds no worker

# Determinism rules
### Context APIs and activities replace calls that change on replay
- Every replay must make the same decisions, so the clock, random values and network calls stay out
- `context.CurrentUtcDateTime`, `context.NewGuid()` and `context.CreateTimer` replace the clock, GUIDs and delays
- **Activities** hold the side effects: `HttpClient`, storage clients and `Random`
- Activities run at least once, so each one must be idempotent
- The Roslyn analyzer reports DURABLE0001 to DURABLE0011 before you merge

# Schedulers, task hubs and SKUs
### Dedicated reserves capacity, Consumption bills per action
- A **scheduler** is the Azure resource; a task hub inside it holds the state of a set of orchestrations
- Each app connects to one task hub, created with the `durabletask` CLI extension
- Dedicated reserves capacity units at a fixed monthly cost, 2,000 actions per second each
- Consumption bills per dispatched action, at 500 actions per second
- Inputs and outputs are limited to 1 MB, instance IDs to 100 printable ASCII characters

# Durable entities for van load
### One entity per van handles its operations one at a time
- An **entity** holds a small piece of state and accepts operations from many callers
- Grey models each van as one `VanLoad` entity keyed by the van ID, such as `van-17`
- A signal is one-way; a call from an orchestrator waits for the result
- Concurrent signals queue up, so no two operations update the state at once
- A read returns a snapshot that can be stale; keep each entity under 1 MB

# Durable timers and the delivery deadline
### A durable timer races the ParcelDelivered event
- `CreateTimer` completes at a future time; the timer is stored with the instance and survives a restart
- Compute the due time from `context.CurrentUtcDateTime`, never `DateTime.UtcNow`
- `WaitForExternalEvent<ParcelDelivered>` and the timer race in `Task.WhenAny`
- When the timer wins, `RaiseDeliveryDelayed` publishes `DeliveryDelayed` to `parcel-events`
- Cancel the timer that loses, because an outstanding timer keeps the orchestration open

# Reroute approval with external events
### The approval races a 24-hour timer, RaiseEventAsync delivers it
- An **external event** is a named message, and the name must match on both sides
- Early events are buffered; events for unknown instances are discarded
- Delivery is at least once, so put a unique ID in the payload
- `RerouteApproved` races a 24-hour timer; a timeout returns reroute declined
- `RaiseEventAsync` or the HTTP `raiseEvent` API delivers the approval behind a function key
