# The sidecar model
### The service calls localhost and the component file picks the store
- Dapr runs as a separate process next to each service
- The service calls its sidecar on localhost: HTTP on port 3500, gRPC on 50001
- Building blocks: service invocation, state, pub/sub, bindings, actors, secrets, configuration
- Each block delegates to a **component**: Cosmos DB, Service Bus or Redis
- `TrySaveStateAsync("statestore", ...)` stays the same in both runs

# Calling a service by app ID
### The sidecar resolves routing-service to a running instance
- Every Dapr app has an **app ID**, shared by all of its replicas
- Callers use `/v1.0/invoke/routing-service/method/reserve-capacity` on the sidecar
- The sidecar resolves the ID through Kubernetes DNS, or mDNS when self-hosted
- `InvokeMethodAsync` handles serialization, `CreateInvokeHttpClient` returns an `HttpClient`
- The `HttpRequestMessage` overloads are obsolete in the current SDK

# Mutual TLS and retries
### Sentry issues the certificates, the resiliency policy decides the retries
- **Sentry** issues and rotates the certificates; application code never handles them
- The AKS extension turns mTLS on by default: 24 h certificates, 15 min clock skew
- Container Apps encrypts invocation between Dapr-enabled apps through the platform
- Retries with backoff come from the resiliency policy for `routing-service`
- When the caller needs no answer, publish an event instead

# ETags and first-write-wins
### A write succeeds only while the ETag still matches
- `GetStateAndETagAsync` returns the value together with its **ETag**
- `TrySaveStateAsync` with `ConcurrencyMode.FirstWrite` returns `false` when another writer won
- The Redis state store throws a `DaprException` for the same conflict
- On a conflict, read again and recompute in a short loop
- After a fixed number of attempts, return a conflict to the caller

# Write modes and transactions
### Choosing a concurrency mode and changing several keys at once
- Without an ETag the newest write replaces the value: **last-write-wins**
- Use first-write-wins for a transition that must happen once
- `StateOptions.Consistency`: eventual by default, strong waits for replicas or a quorum
- `ExecuteStateTransactionAsync` succeeds for every key or fails for every key
- `state.azure.cosmosdb` is Tier 1 and needs the partition key path `/partitionKey`

# Publishing and subscribing
### The code names the component pubsub and the topic parcel-events
- `PublishEventAsync("pubsub", "parcel-events", scan)` names no broker
- `[Topic("pubsub", "parcel-events")]` or `WithTopic` declares the subscription
- `MapSubscribeHandler` lists the subscriptions, `UseCloudEvents` unwraps the **CloudEvents** envelope
- Swap the broker in the component file: Service Bus, Event Hubs, Redis or Kafka
- Use the native Service Bus SDK when the logic depends on session state

# Dead-letter topics
### Messages that still fail after the retries land on poison-scans
- Declare a subscription in a `dapr.io/v2alpha1` `Subscription` file or in code
- `deadLetterTopic: poison-scans` takes what still fails after the retries
- The resiliency spec controls how Dapr retries
- Service Bus dead-letters a message after the default `MaxDeliveryCount` of 10
- `maxDeliveryCount` takes effect only when Dapr creates the subscription
