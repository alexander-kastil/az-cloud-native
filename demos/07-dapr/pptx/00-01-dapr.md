# Dapr building blocks for portable services

## Content

- **Sidecar and service calls**: Dapr beside each service in the Aspire AppHost, calls by app ID
- **State and events**: ETag checks on writes, pub/sub through a broker set in a component file
- **Policies, actors and hosting**: retries and breakers, one `VanActor` per van, Container Apps or AKS

## Speaker Notes

Modules 4 to 6 connected Grey Logistics to Service Bus, Event Hubs and Cosmos DB through their Azure SDKs. This module runs the same flow through Dapr building blocks, and the component files decide which Azure service sits behind each call.

Sidecar and service calls: every service gets a Dapr sidecar from the Aspire AppHost, and services call each other by app ID instead of a host name.

State and events: state writes carry ETag checks, and events go through a pub/sub component whose broker you can swap without touching the code.

Policies, actors and hosting: retry and circuit breaker rules live in one resiliency spec, each van becomes a `VanActor`, and the last topic decides whether a service belongs on Container Apps or AKS.
