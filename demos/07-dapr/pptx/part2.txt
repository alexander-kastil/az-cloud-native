# The resiliency spec
### Named policies in one file, applied to calls to routing-service
- `policies` names timeouts, retries and circuit breakers; `targets` attaches them
- `general`: each attempt waits at most 5 s
- `retryPolicy`: constant 2 s delay, 3 retries, only status codes 500 to 599
- A full call can take the timeout times the attempts, plus the delays
- The sidecar loads the file only when the AppHost sets `ResourcesPaths`

# How the circuit breaker opens and closes
### cbPolicy trips after five consecutive failures
- `trip: consecutiveFailures >= 5` opens the breaker
- While open, the breaker rejects calls at once for its `timeout` of 60 s
- Half-open lets `maxRequests` (1) probe through, and a success closes it
- `interval` stays at 0 s, so nothing clears the count while the breaker is closed
- Dapr creates breakers per component and per app instance

# Resiliency targets
### Policies keyed by app ID, actor type or component name
- `apps` keys policies by app ID, `actors` by actor type, `components` by component name
- `outbound` protects the call to the store, `inbound` the delivery to your app
- Container Apps offers **Dapr component resiliency** as a preview feature
- `az containerapp env dapr-component resiliency create` attaches a policy to a component
- Service discovery resiliency does not apply to Dapr service invocation

# Virtual actors and turn-based access
### Each van is an actor that handles one call at a time
- The runtime activates an actor on the first request for its ID
- Idle actors are garbage-collected and come back with their saved state
- Calls run one at a time, so two assignments for `van-42` never share a free slot
- `IVanActor` derives from `IActor`, `VanActor` from `Actor`; callers use `ActorProxy.Create`
- All actor types share one **actor state store** that supports transactions

# Timers and reminders
### A heartbeat while the actor is active, a service check that survives deactivation
- `RegisterTimerAsync`: a heartbeat every 5 s, only while the actor is active
- `RegisterReminderAsync`: `van-service-check` every 24 h, persisted in the state store
- The runtime calls `ReceiveReminderAsync` for every reminder that fires
- Reminders cost more than timers, because the runtime writes them to storage
- Container Apps does not run the actor packages: use the AppHost or AKS

# Dapr on Container Apps
### Components live on the environment and scopes pick the app IDs
- `--enable-dapr` and `--dapr-app-id` turn Dapr on per app
- Components are defined once on the environment and scoped to app IDs
- Tier 1 and Tier 2 only: Cosmos DB state and Service Bus topics are **Tier 1**
- The platform picks and upgrades the Dapr version, with a suffix such as `-msft.1`
- No actor or workflow SDK packages, and no Dapr for jobs or Container Apps Express

# Choosing Container Apps or AKS
### Four questions decide where a service runs
- AKS installs Dapr as the `Microsoft.Dapr` cluster extension
- The extension supports the current and the previous Dapr version
- Pin a version with `--version` and `--auto-upgrade-minor-version false`
- High availability and mTLS are on by default: three control-plane replicas
- Container Apps for stateless Tier 1 services, AKS for actors and pinned versions

# Takeaways
### What to carry into durable execution
- The code names a component, and the component file picks the Azure service
- Call services by app ID and leave the retries to the resiliency spec
- Write once-only transitions with an ETag and first-write-wins
- Give each van a `VanActor`, hosted on the AppHost or AKS
- Stateless Tier 1 services go to Container Apps, actors and pinned versions to AKS
